# bd8 i16-lane inverse transform on NEON — measured (2026-07-28, Apple M4 Pro)

Before/after around `674b36b` ("bd8 i16-lane transform passes run on aarch64"),
base `101784b`. Port-only harness (`aom-dsp-bench`, no C oracle). Full method,
host, commands and load in `dsp_neon_i16_2026-07-28.meta`; all 4 × 77 per-cell
deltas in `dsp_neon_i16_2026-07-28.tsv`.

## Read the control band FIRST

`AOM_FORCE_SCALAR=1` is not a scalar baseline on aarch64, so this is a
two-BUILD pair. Two-build pairs on this box carry real cross-run noise, and a
single small-cell row proves nothing. The negative control here is the strongest
kind available: **the same `before` binary re-run against its own saved
baseline**, twice.

| | min | median | max |
|---|---|---|---|
| ctrl1 (before vs before) | −2.81% | +1.61% | **+16.52%** |
| ctrl2 (before vs before) | −3.74% | +0.25% | **+5.01%** |
| after1 (after vs before) | −51.25% | +1.34% | +29.32% |
| after2 (after vs before) | −49.75% | +2.00% | +7.32% |

So on this box a same-binary row can move up to +16.5%, and the noisiest
cells — the sub-30 µs `dist`, `quant`, `intra` batches — swing ±10–29%
run to run. `dist::sad_64x64` reads +29.32% in after1 and +1.29% in after2;
`intra::v_16x16` reads +16.52% in ctrl1 (same binary!) and +3.82% in after2.
**Every "regression" this run reports outside the transform groups is inside
that band.** The i16 change cannot touch `dist`/`quant`/`intra`/`cdef`/
`loopfilter` — it is confined to `transform/simd/{lowbd16, prims16,
inv1d_v3_i16_gen}` behind the bd8 inverse entry points.

## The lever: `inv_txfm_u8`, DCT cells

The i16 path fires only for bd8 inverse DCT (`idct4/8/16/32/64` — the five
kernels `xtask/audit_i16_safety.py` clears). Every other cell in the same
group is an in-group paired control, measured in the same interleaved rounds:
ADST cells never take it, and `inv_txfm_hbd10` is bd10 so the entry conditions
(row/col clamp 16, `stage_range` all 16) fail.

| cell | after1 | after2 | ctrl1 | ctrl2 | verdict |
|---|---|---|---|---|---|
| `32x32_dct` | **−51.25%** | **−49.75%** | −0.08% | +2.45% | win |
| `16x16_dct` | **−47.10%** | **−44.69%** | +0.31% | +2.50% | win |
| `64x64_dct` | **−45.80%** | **−45.43%** | −0.06% | +1.94% | win |
| `16x08_dct` | **−25.85%** | **−25.26%** | +0.78% | +2.15% | win |
| `32x08_dct` | **−23.43%** | **−21.49%** | +0.99% | +2.55% | win |
| `04x16_dct` | −6.44% | −3.65% | +0.20% | +2.69% | win (small) |
| `08x08_dct` | +3.16% | +5.25% | +0.45% | +3.11% | neutral |
| `04x04_dct` | +2.80% | +5.00% | +1.95% | +5.01% | not on the path |

| `04x16_adst` | +1.58% | +3.06% | +0.57% | +2.31% | control |

Both after-runs agree to within 2.4 points on every winning cell, and all five
big wins are 3–20× outside the control band. Throughput on the headline cells
(before → after1, from the two runs' own `px/s` columns): `16x16_dct`
594M → 1.12G, `32x32_dct` 518M → 1.06G, `64x64_dct` 442M → 815M,
`16x08_dct` 544M → 733M, `32x08_dct` 542M → 706M.

Two honest non-wins:

* **`08x08_dct` is neutral, not a regression.** It does take the new i16
  column path (`col_n == 8`, half the lanes idle; the row pass declines
  because `row_n % 16 != 0`). Its `+3.16/+5.25` is indistinguishable from its
  own ADST twin's `+3.14/+5.52` measured in the same rounds — the two move
  together, so there is no DCT-specific effect at 8×8 in either direction.
  Not worth gating out on this evidence; a dedicated 8-wide measurement is
  chunk-2 work.
* **`04x04_dct` never reaches the i16 path at all** — `half_batch_pays(4)` is
  false on aarch64, so `try_inv_col_pass_u8` declines before the i16 arm. Its
  `+2.80/+5.00` against a `+1.95/+5.01` control is the box, and it is a useful
  witness for exactly how much the box moves.

## Why it wins (and why 16x16/32x32/64x64 win most)

Two effects compose, and the sizes that win most are the ones that get both:

1. **Lane count.** 16 columns (or rows) per vector where the i32x8 pass gets
   8 — one batch instead of two. Needs `col_n % 16 == 0` (col pass) or
   `row_n % 16 == 0` (row pass), which is why 16/32/64-wide cells win and
   8-wide does not.
2. **`half_btf` cost, which is the bigger one on NEON.** The i32 tier's `hb`
   has to widen to i64 to sum exactly (`vmovl_s32` ×4, `vaddq_s64` ×4,
   `vshlq_s64` ×2, `vmovn_s64` ×2, …) — roughly 15 instructions per 8 lanes,
   30 per 16. On the audited i16 domain no widening is needed at all: the
   products fit i32, so `vmull_n_s16` / `vmlal_n_s16` / `vrshrq_n_s32::<12>`
   do the whole butterfly in **12 instructions per 16 lanes**. That is ~2.5×
   less work for the dominant operation, and it applies per batch regardless
   of how many lanes are active — which is why even the rectangular 16×8 and
   32×8 cells (col pass only, row pass declines) still take −21..−26%.

Saturating add/sub (`vqaddq_s16`) replacing `clampv`'s min+max on two i32
registers is a third, smaller multiplier on the same axis.

## Comparison to the x86 landing

The AVX2 i16 column pass measured −31.5% on the column pass in
`gate3_transform_simd_2026-07-17.md`, and the AVX2 row pass added its own
increment in `bd8_i16_rows_2026-07-23.md`. The ARM whole-transform numbers
here are larger (−45..−51% on the square cells) because effect (2) above is
much bigger on NEON than on AVX2: `vpmaddwd` already gave the AVX2 i32 path a
cheap exact butterfly, whereas NEON's i32 `hb` pays for a full i64 round trip
that the i16 path deletes outright.

## Not measured here

* x86-64. Nothing on that side changed instruction-wise (the `prims16::x86`
  module is the verbatim AVX2 sequences that shipped in `lowbd16.rs`), and no
  AVX2 box was available; `cargo check --target x86_64-apple-darwin` clean is
  the only x86 claim made.
* Whole-decode wall (`aom-bench`'s `gate3`) — that harness needs the C oracle
  and a quiet box. The transform is a single stage of the decode loop, so the
  kernel-level −45..−51% translates to a much smaller frame-level number; do
  not extrapolate one from the other.
* A 4×8 cell still does not exist in `TX_CELLS` (open since 2026-07-25), so
  `half_batch_pays(8)` remains interpolated.
